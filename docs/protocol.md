# Ninebot BLE protocol notes

This document describes the wire protocol used by Ninebot (Segway) eKickScooters, as implemented
by this library. It applies to both protocol generations the library supports and is based on the
[miauth](https://github.com/dnandha/miauth) reference implementation, the ScooterHacking.org wiki
and live captures from real scooters.

## Transport

All communication uses the Nordic UART service:

| Direction | UUID |
| --- | --- |
| Service | `6e400001-b5a3-f393-e0a9-e50e24dcca9e` |
| Write (client → scooter) | `6e400002-b5a3-f393-e0a9-e50e24dcca9e` |
| Notify (scooter → client) | `6e400003-b5a3-f393-e0a9-e50e24dcca9e` |

Writes are chunked to 20 bytes per BLE write. Notifications can contain a whole frame, a fragment,
or several concatenated frames; the client reassembles and re-syncs on the `5A A5` magic.

## Discovery

Scooters advertise in different ways depending on generation:

- Classic generations: manufacturer id `0x424E` (16974), local name like `NBScooter...`
- Newer generations (x3, e.g. E3/E3 Pro, G3): manufacturer id `0x434E` (17230), local name is the
  scooter serial number (e.g. `1TEFE2517C0419`)
- Some models skip manufacturer data entirely and only expose the Nordic UART service with the
  serial-style name

The library's `is_scooter_advertisement()` accepts all three shapes.

## Frame format

Every frame starts with the magic `5A A5`, followed by a 5-byte header and the payload:

```
5A A5 | len | src | dst | cmd | data_index | payload ...
```

| Offset | Field | Meaning |
| --- | --- | --- |
| 0–1 | magic | always `5A A5` |
| 2 | `len` | payload length in bytes (total frame = `len + 7` before checksum/crypto trailer) |
| 3 | `src` | source device id |
| 4 | `dst` | target device id |
| 5 | `cmd` | command |
| 6 | `data_index` | register address, or handshake sub-command |
| 7… | payload | register data, keys, serial numbers, … |

Device ids used by the client (`src` is always `PC` = `0x3D`):

| Id | Device |
| --- | --- |
| `0x20` | master controller (register target for `CtrlIdx`) |
| `0x21` | BLE module (handshake target) |
| `0x22` | battery/BMS (register target for `BmsIdx`) |
| `0x3D` | PC / host |
| `0x3E` | phone (used by vendor apps; some replies use it) |

Commands:

| Value | Command | Meaning |
| --- | --- | --- |
| `0x01` | READ | read register (`payload[0]` = bytes to read, `data_index` = address) |
| `0x02` | WRITE | write register, with reply |
| `0x03` | WRITE (no reply) | write register, no reply |
| `0x04` | READ_ACK | reply to READ |
| `0x05` | WRITE_ACK | reply to WRITE |
| `0x5B` | INIT | handshake: request session key |
| `0x5C` | PING | handshake: session check / pairing state |
| `0x5D` | PAIR | handshake: pairing request/confirm |

Frames with unknown device ids or commands are skipped (never fatal) because models and firmware
generations differ.

## Protocol generations

### Encrypted protocol (recent firmware)

Used by most modern firmware (Max G30 family, F-series, E-series, x3 generation like E3/E3 Pro,
and others). The handshake:

1. **INIT** (→ BLE module). The scooter replies with a 24-byte payload: a random 16-byte *BLE key*
   followed by the scooter's serial number.
2. Both sides derive the session key as `SHA1(name || ble_key)[0:16]`, where `name` is the BLE
   advertisement name of the scooter. Frames are encrypted with AES-128-ECB in a counter-like
   stream mode with a CRC and message counter appended (implemented by
   [miauth's `NbCrypto`](https://github.com/dnandha/miauth/blob/master/miauth/nb/nbcrypto.py)).
3. **PING** with a random 16-byte *app key* generated by the client. The reply's `data_index`
   tells the pairing state:
   - `data_index = 1`: the scooter already accepts this session. Both sides switch to the
     app-key-derived session (`SHA1(app_key || ble_key)[0:16]`) and finish with one final PAIR.
   - `data_index = 0`: not paired yet. The client repeats **PAIR** (payload = serial number) and
     waits for the user to **short-press the scooter's power button** as confirmation. Two
     confirmation styles exist in the wild:
     - a fresh PING ack with `data_index = 1` → switch to the app key and send a final PAIR, or
     - a PAIR ack with `data_index = 1` → the session simply continues on the BLE key and no
       further PAIR may be sent.
4. Register READ/WRITE traffic then flows over the encrypted channel.

The INIT ack itself is encrypted with the pre-handshake key (`name || FW_DATA`), where `FW_DATA`
is the 16-byte constant `97 CF B8 02 84 41 43 DE 56 00 2B 3B 34 78 0A 5D`.

Pairing is per-session; the scooter does not permanently bind to the client. If the user does not
press the button within 60 seconds, the client gives up and disconnects.

### Legacy plain protocol (old firmware)

Old firmwares (early ES-series and friends) only understand plain frames: the same `5A A5` frame
format, unencrypted, with a 2-byte little-endian checksum appended after the payload. The checksum
is the inverted 16-bit sum of all bytes from offset 2 (inclusive) to the end of the payload:

```
checksum = (~sum(frame[2:-2])) & 0xFFFF   # appended low byte first
```

Legacy scooters pair with a single PAIR exchange and need no crypto. Because they ignore
encrypted frames, the client probes plain first (short timeout) and falls back to the encrypted
handshake when nothing answers.

## Register reads

A register read is a READ frame to the controller (`0x20`) or battery (`0x22`) with
`data_index = register address` and one payload byte = number of bytes to read (2 here). Multi-word
registers (32-bit values) occupy consecutive addresses and are read as several 16-bit words
combined little-endian.

The register tables in [`ninebot_ble/register.py`](../ninebot_ble/register.py) are the source of
truth. Summary of the controller registers:

## Model detection

The scooter serial number (14 characters, e.g. `N4GSD1939C0123`) encodes the model:

```
N4G  S  D  19 39  C  0123
 aaa  b  c  yy ww  r  nnnn
```

| Part | Meaning |
| --- | --- |
| `aaa` (0–2) | product identifier (model series), e.g. `N4G` = Max, `1TE` = E3 family |
| `b` (3) | product version (model variant within the series) |
| `c` (4) | manufacturing line |
| `yy ww` (5–8) | production year and ISO week |
| `r` (9) | product revision |
| `nnnn` (10–13) | weekly unit number |

The mapping lives in [`ninebot_ble/serial_parser.py`](../ninebot_ble/serial_parser.py) and follows
the [ScooterHacking.org wiki](https://wiki.scooterhacking.org/). The x3 generation is covered at
family level (`1TE` → E3 / E3 Pro, `1CG` → Max G3); the variant letters within those families are
not publicly documented yet. Unknown serials degrade to `<series>-series` instead of failing.
